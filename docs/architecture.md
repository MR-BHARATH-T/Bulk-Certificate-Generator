# Bulk Certificate Generator Architecture

## Overview

The Bulk Certificate Generator is a system designed to accept large batches of recipients via a single API request, validate the data, and asynchronously generate customized PDF certificates. The system is designed to be fault-tolerant, ensuring that individual recipient failures do not halt the entire batch process.

## Technology Stack

- **Backend**: Python 3.12, FastAPI, Uvicorn
- **Database**: PostgreSQL (via Supabase) with SQLAlchemy 2.x and Alembic
- **PDF Generation**: ReportLab
- **Frontend**: React (Vite)
- **Deployment**: Render (Backend), Vercel (Frontend), Supabase (Database & Storage)

## Architecture Components

### 1. API Layer (FastAPI)
- Handles incoming HTTP requests.
- Validates request payload using Pydantic schemas.
- Records the job and recipients in the database (status: `PENDING`).
- Returns immediate `202 Accepted` response with the job ID for asynchronous processing.
- Exposes endpoints to retrieve job status, recipient details, and download certificates.

### 2. Job Processing Worker
- Periodically polls the database for `PENDING` jobs or recipients.
- Uses atomic database row locking (`FOR UPDATE SKIP LOCKED`) to claim work and prevent duplicate processing.
- Validates individual recipient data, rendering a PDF certificate via ReportLab if valid.
- Uploads the generated PDF to Supabase Storage.
- Updates recipient and job statuses to track progress (`PROCESSING`, `COMPLETED`, `FAILED`).
- Implements retry logic for transient errors (e.g., storage upload failures).

### 3. Database Layer (PostgreSQL)
- Stores metadata about jobs and individual recipients.
- **`generation_jobs` Table**: Tracks overall batch progress (total, valid, completed, failed counts).
- **`recipients` Table**: Tracks individual recipient status, error messages, and storage paths.

### 4. Storage Layer (Supabase Storage)
- Stores generated PDF certificates securely.
- Certificates are accessed via temporary signed URLs generated by the API, ensuring they are not publicly exposed indefinitely.

## Data Flow

1. **Job Creation**: Client submits a POST request to `/api/v1/jobs`. The API validates the batch, inserts a `generation_jobs` record and multiple `recipients` records, and responds with a Job ID.
2. **Background Processing**: The worker picks up the job. For each recipient, it generates the PDF, uploads it, and updates the database.
3. **Status Polling**: Client polls GET `/api/v1/jobs/{job_id}` to see progress.
4. **Certificate Download**: Once completed, the client can request a signed URL for an individual certificate or a ZIP containing all successful certificates.

## Database Schema (Proposed)

### `generation_jobs`
- `id`: UUID (Primary Key)
- `event_name`: VARCHAR
- `organization_name`: VARCHAR
- `issue_date`: DATE
- `status`: ENUM ('PENDING', 'PROCESSING', 'COMPLETED', 'PARTIALLY_COMPLETED', 'FAILED')
- `total_count`: INTEGER
- `valid_count`: INTEGER
- `completed_count`: INTEGER
- `failed_count`: INTEGER
- `created_at`: TIMESTAMP
- `started_at`: TIMESTAMP
- `completed_at`: TIMESTAMP

### `recipients`
- `id`: UUID (Primary Key)
- `job_id`: UUID (Foreign Key to generation_jobs)
- `full_name`: VARCHAR
- `email`: VARCHAR (Optional)
- `certificate_id`: VARCHAR (Unique, e.g., standard format for verification)
- `status`: ENUM ('PENDING', 'PROCESSING', 'COMPLETED', 'FAILED')
- `storage_path`: VARCHAR
- `error_code`: VARCHAR
- `error_message`: TEXT
- `attempt_count`: INTEGER
- `created_at`: TIMESTAMP
- `completed_at`: TIMESTAMP
